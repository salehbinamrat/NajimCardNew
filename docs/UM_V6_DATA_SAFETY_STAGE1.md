# المرحلة الأولى: سلامة بيانات User Manager v6

## الأساس والنطاق

تم جلب `main` والتحقق مباشرة من مرجعه قبل العمل. أحدث التزام متاح كان
`fdfc59d4de215eee14028aef248f0ccb0819d449`، وهو دمج PR #38؛ لم توجد إصلاحات
لاحقة على `main` وقت المراجعة. احتُفظ بإصلاحاته: طلب عدادات v6 الأصلية، وأولوية
الزوج الأصلي الصحيح، وقراءة احتياطية واحدة عند نقص الحقول.

هذا التغيير يقتصر على سلامة القراءة والتصنيف والحذف المشروط في v6 وعرض الحقول
غير المؤكدة. لا يغير مخطط SQLite أو بيانات المستخدمين المحفوظة أو بروتوكول إنشاء
الكروت أو الطباعة أو الترخيص، ولا يتضمن المرحلة الثانية.

## الأخطاء المثبتة والإصلاح

- كانت معرفات الباقات تتحول إلى اسم مشترك، فتختلط حدود ملاك مختلفين. أصبح الربط
  يحتفظ بالمعرف والمالك، ولا يقبل اسمًا ملتبسًا أو رابطًا عابرًا للمالك.
- كان غياب `disabled` أو `incomplete` يقبل كأنه `false`. أصبح تحقق الحقلين
  صريحًا، ولا يكون الحساب غير المتحقق مؤهلًا لتصنيف مؤكد أو حذف المنتهي.
- كان التحقق يقبل عدادات بديلة بينما الحساب يقرأ عدادًا أصليًا تالفًا. تستخدم
  القراءتان الآن إجراء واحدًا: زوج أصلي صحيح، وإلا زوج بديل صحيح، دون خلطهما.
- الروابط المفقودة والحدود التالفة والملكية المجهولة أصبحت بيانات غير مؤكدة،
  وليست حدودًا صفرية. الصفر الصريح الصحيح أو باقة متحققة بلا قيود يبقيان مدعومين.
- الجلسات المفقودة تعرض «غير متاح»، والحدود أو المتبقي غير المتحققين يعرضان
  «غير مؤكد»، في الحسابات وتفاصيل اللوحة والكروت.
- الحذف يعيد قراءة المخزون والتعريفات خارج الذاكرة المؤقتة، ثم يتحقق من كل حساب
  بالمعرف ويعيد قراءة التعريفات قبل أمر الحذف. يطابق المالك ومعرف الباقة والحد
  والهوية والحالة الإدارية والاستهلاك. فشل القراءة لا يعني إرسال أمر حذف، ولا
  يعيد قائمة قديمة باعتبارها متحققة. انقطاع تأكيد كتابة لا يؤدي إلى إعادة إرسالها.

## دليل الاختبارات أولًا

أضيف `UserManagerV6DataSafetyTests` قبل تعديل الكود الإنتاجي: فشلت 25 حالة من 29
على الأساس الحالي. ثم أثبت اختباران إضافيان خلط روابط شاشة الباقات وتغير حدود
الباقة أثناء الدفعة قبل إصلاحهما. وثبتت ثلاث حالات إضافية لفشل القراءة ورصيد
المتبقي المجهول قبل إصلاحها. وأثبتت ثلاث حالات أن تجاهل حالة الأحرف قد يربط
هويات مختلفة، فأصبحت مطابقة أسماء الملاك والباقات حرفية. الحالات الإيجابية تحافظ على دعم الإصدار السادس
والعدادات الأصلية الصحيحة والقيم الصفرية الصريحة.

يتضمن الملف الجديد 40 حالة تغطي خصوصًا مالكين وباقتي `gold` بحدي 1000 و100 MiB،
وكرت المالك الأول باستهلاك 500 MiB، والحقول الإدارية المفقودة/التالفة، والعدادات
البديلة، والقيد المفقود، والجلسات المجهولة، وتجدد الكرت وتغير المالك والحدود قبل
الحذف وأثناء الدفعة. عُدلت تجهيزات الاختبارات القديمة لإضافة بيانات الملكية
والحالة الإدارية التي كانت محذوفة من المحاكاة؛ لم تُخفف شروط الأمان لتمريرها.

كل عمليات الحذف في الاختبارات استدعاءات لكائنات وهمية داخل الذاكرة. لم تُستخدم
بيانات اتصال أو عمليات حذف على MikroTik حقيقي. نتائج Windows النهائية وروابط
الحزم تُوثق في طلب الدمج؛ البوابة الحالية تشغّل Core وRelease بالتوازي وتمنع
بناء الحزم حتى نجاحهما.

## حدود التحقق وتكلفة الأمان

التحقق قبل كل حذف يضيف قراءة حساب موجهة وثلاث قراءات لتعريفات الباقات والقيود
والروابط؛ لا يعيد تنزيل جدول المستخدمين كاملًا لكل كرت. هذا مقصود حتى لا تُستخدم
حدود بداية دفعة طويلة بعد تغييرها. لا يتضمن هذا الطلب تحسين سرعة الإرسال.

RouterOS API لا يقدم معاملة ذرية تجمع قراءات التحقق وأمر الحذف؛ تظل هناك نافذة
تزامن صغيرة إذا عدّل مسؤول آخر الحساب أو التعريفات بين آخر قراءة والأمر. الكود
يرفض كل نقص أو تغير يرصده، ولا يدعي إلغاء هذه الخاصية في بروتوكول الراوتر.
توافق الردود مع راوتر حقيقي لم يُختبر ميدانيًا؛ إذا حذف إصدارٌ حقول المالك أو
الحالة حتى في القراءة الكاملة، تظهر الحالة غير مؤكدة ويُمنع الحذف بدل افتراضها.

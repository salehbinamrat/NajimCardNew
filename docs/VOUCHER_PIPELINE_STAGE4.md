# المرحلة الرابعة: دورة إنشاء الكروت وإرسالها وحفظها

الأساس المعتمد: `7f3b92b4656eb8fa14052b87cb493766b3fd1d6b`، بعد دمج PR #41 بموافقة المستخدم. النطاق هو دورة الإصدار فقط؛ لا بدء للمرحلة الخامسة.

## الأخطاء المثبتة والاختبارات أولاً

ظهرت ست حالات فشل قبل أول تعديل إنتاجي، وثلاث حالات إضافية قبل إصلاح غياب الخدمة المختارة، وحالتان قبل تصحيح فحص ملكية الباقة عند الإصدار:

- وجود رقم واحد متاح بين 65,536 احتمالاً لا يضمن نجاح محاولات التوليد الـ200 القديمة. كذلك فشلت محاولة ملء آخر ثلاثة أرقام في مساحة 10,000 رقم.
- كان الحفظ المحلي يسبق فحص أسماء الراوتر، ويقتصر الحجز المحلي على الخدمة المختارة.
- كان غياب قائمة الخدمة المختارة يُفسّر باعتباره قائمة خالية؛ أصبح يمنع اعتماد الدفعة. يمكن تجاهل غياب الخدمات الأخرى غير المثبتة فقط، مع استمرار منع تجاوز أخطاء الصلاحيات أو الاتصال.
- قراءة هوية الراوتر تكررت 101 مرة عند التثبيت مرة والتحقق 100 مرة على الاتصال نفسه. يُعاد الآن استعمال الدليل داخل الاتصال المصادق نفسه فقط؛ كل اتصال بديل يخضع للتحقق قبل أي أمر، كما في المرحلة الثانية.
- إيصال PPPoE وحده كان يُعلن النجاح دون قراءة الحساب وباقته. صار كل إصدار عبر المرسل الدائم، بما فيه Hotspot، يتطلب إيصالاً صالحاً وقراءة بالمعرف تطابق الاسم والباقة والخدمة والحالة الإدارية.
- كان تأكيد UM يقبل غياب المالك. أصبح التأكيد يتطلب مالكاً محدداً يطابق المختار؛ عند نقص الإسقاط تجري قراءة توافق واحدة بالمعرف نفسه.
- فحص جاهزية UM كان يرفض الباقة الصحيحة إذا وُجدت باقة بالاسم نفسه لمالك آخر، ويسمح بمالك مجهول. أصبح يتطلب تطابقاً واحداً مؤكداً للمالك المختار؛ لم يتغير منطق الحذف المستقل للمرحلة الأولى.
- استعلام استعادة UM v6 بالاسم كان غير موجود في قائمة النقل المسموحة. أضيف `?username=` على قائمة v6 فقط، واختُبر على TCP محلي؛ مهلة طلب السجل الواحد 20 ثانية.

الاختبارات السلوكية الجديدة في `VoucherPipelineStage4Tests` و`VoucherExecutionStage4Tests` و`VoucherPreparationStage4Tests` و`VoucherPipelineSafetyStage4Tests`. تحقق أيضاً من عدم رفع عداد التأكيد عند فشل COMMIT، وتوقف الدفعة عند UNKNOWN، وبقاء SENDING بعد الفشل، وعدم إعادة الإضافة أو التفعيل بعد إعادة التشغيل أو المطابقة. اختبارات المرحلتين السابقتين تبقى جزءاً من CI.

## التنفيذ وضمانات السلامة

- أخذ عينات تشفيرية دون استبدال من رتب الأرقام المتاحة باستخدام Fisher–Yates متناثر وBigInteger. البحث بين الأرقام المحجوزة لوغاريتمي؛ لا مسح لمساحة أسماء ضخمة ولا بذور متوقعة ولا تخفيض لطول كلمة المرور. جرى الحفاظ على أوضاع بيانات الدخول الثلاثة.
- `VoucherBatchPreparer` يقرأ جميع خدمات الراوتر قبل التوليد والحفظ. يحجز الأسماء المحلية عبر الخدمات للراوتر نفسه، ويحجز السجلات القديمة مجهولة الملكية تحفظياً دون نسبتها إلى راوتر. يعيد فحص التعارض المحلي داخل معاملة الحفظ نفسها.
- فحص الراوتر يُعاد عند الإرسال، لأن المستخدم قد ينتظر بعد الإنشاء. لا توجد معاملة موزعة بين SQLite وRouterOS؛ لا يمكن منع تغييرات عميل خارجي بين القراءات. تظل النتائج غير المؤكدة ممنوعة من الإرسال مجدداً حتى المطابقة المستقلة.
- تنفيذ دفعة واحدة في كل بوابة في الوقت نفسه. أوامر دورة الإصدار عبر النقل الحقيقي تخضع لحد محافظ قدره **20 أمراً/ثانية**، بلا دفعات اندفاعية لتعويض التأخير. القراءات والإضافات والتفعيل والتأكيد ضمن الدورة تدخل في العداد؛ لا تتغير حركة الصفحات غير التابعة للدورة.
- التحقق فوري أولاً، ثم خمسة فحوص كحد أقصى عند نتيجة معلقة فقط، عند 0/50/150/350/750 مللي ثانية من بدء التحقق. زمن الرد نفسه يستهلك الانتظار؛ لا يُضاف انتظار ثابت بعد رد بطيء. الميزانية الكلية **20 ثانية** تشمل القراءة والانتظار. تضارب الهوية أو الملكية أو باقة أخرى غير فارغة يوقف التحقق مباشرة. لا إعادة لأي كتابة مجهولة النتيجة.
- حفظ الدفعة يستخدم INSERT محضراً لسجل الأحداث، وتسجيل الدفعة مرة واحدة، وتجهيز DPAPI قبل حجز كاتب SQLite. استمر WAL و`synchronous=FULL`، ومعاملة SENDING مستقلة قبل الشبكة ومعاملة نتيجة مستقلة بعدها لكل كرت. لم تُجمّع الإيصالات في COMMIT مؤجل.
- تقدم الواجهة يعرض SENT المحفوظ فعلياً، والفاشل والمجهول. النسبة تعتمد على المؤكد، ولا تصل إلى 100% عند فشل أو غموض. عدد تحديثات الدفعات الكبيرة محدود؛ لا مؤقت يحرك عداداً افتراضياً.
- قياسات رتيبة لكل مرحلة: Generation، NameCheck، SQLite، Add، Activation، Verification، Save، Print، إضافة إلى Identity وReadiness. SQLite هنا يقيس معاملات الحفظ والإرسال، بما فيها DPAPI؛ الإجمالي يشمل أعمال القراءة والواجهة الأخرى أيضاً. أوقات الطباعة تعني إنشاء المستند/render وتسليمه للنظام أو تصديره، ولا تعني خروج الورق من الجهاز.
- عداد API يقيس محاولات أوامر الدورة قبل الكتابة إلى النقل، بما فيها طلبات إعادة الاتصال عند وقوعها. إعادة القراءة الآمنة منفصلة عن إعادة فحص ظهور الباقة. لا تُسجل الأسماء أو كلمات المرور في ملف القياس.
- قياسات عملية الإنشاء/الإرسال/الحفظ تحفظ في `%LOCALAPPDATA%/NajmCardNew/Data/Performance` بصيغة JSON. الحالات ومحاولات الإرسال ومعرفاتها وتوقيتها تبقى في سجل الدفعات المعتاد.

لم تتغير آلية الترخيص أو قالب الطباعة أو دقة PDF أو قاعدة بيانات حضرموت. تعديل الطباعة وإكسل/CSV اقتصر على إضافة القياس؛ حفظ باقة الطباعة لا يزال مع الكروت في المعاملة نفسها.

## المقارنة القابلة للتكرار

`tools/VoucherPipelineBenchmarks` يشغل المولد والمرسل وSQLite الحقيقيين مع راوتر داخل العملية لا يملك خيار عنوان شبكة. الخدمات الثلاث، وأحجام 1 و100 و1000 و10000، وتسخين ثم ثلاث عينات ووسيط زمنها. كلمات المرور فارغة وفق نمط username-only لتشغيل المقارنة نفسها على Linux وWindows؛ اختبارات Windows المنفصلة تتحقق من DPAPI والأوضاع الثلاثة.

`instrument_baseline.py` يتحقق من SHA الأساس ويضيف مؤشرات قياس فقط إلى نسخة منفصلة منه. لا يغيّر خوارزمية الأساس أو ترتيب استعلاماته أو انتظار التفعيل أو حدود المعاملات. خط الأساس يحتفظ بالحفظ قبل فحص الراوتر كي تظهر كلفة ضمان الحفظ الجديد صراحة.

الزمن المحلي أدناه زمن المحاكاة ومعالجة البيانات وSQLite على بيئة التطوير، وليس زمن MikroTik. يوجد نموذج منفصل يفترض 50 ms لكل أمر على اتصال متسلسل؛ لا يُقدَّم باعتباره زمناً مقاساً للشبكة. حد 20 أمراً/ثانية قد يزيد الانتظار على شبكة محلية أسرع، وهو مقصود لحماية الراوتر؛ لا ادعاء بأن كل سيناريو أصبح أسرع. تكلفة ضمان التوليد والتأكيد أقرب إلى بضعة مللي ثانية، وتختلف أزمنة fsync بحسب القرص.

## التحقق والبناء

محلياً: 487 Core و56 Delivery و261 Python ناجحة؛ ترجمة الحل وWPF وأداة PDF ناجحة. أضيفت 30 حالة سلوكية مقارنة بالمرحلة الثالثة. الاختبارات الهيكلية القديمة حُدثت لتتبع مكان التحقق الجديد وحدود الانتظار الجديدة، مع إبقاء اختبارات السلوك والتلف والانقطاع والحفظ.

Windows Core وWindows Release يعملان بالتوازي على SHA واحد. لكل منهما مقارنة محلية قبل/بعد على Windows runner نفسه. Release يشغل أدوات القياس أيضاً بإصداري x86/x64 self-contained. بناء Portable وInstaller لكل معمارية ينتظر نجاح جميع الاختبارات ومقارنات دورة الإصدار وPDF والمقارنة الموروثة لطبقة الجلب. لا يُسمح بفقد كرت أو زيادة غير مبررة في طلبات API أو غياب تحقق الحساب؛ الأزمنة تُعرض دون حد هش مرتبط بسرعة جهاز CI.

كشف التشغيل الأول على Windows نقص تحميل موارد WPF في أداة قياس PDF المستقلة (`DarkComboBox`)، بعد نجاح جميع اختبارات التطبيق. صُححت تهيئة الأداة بتحميل قواميس `App.xaml` نفسها دون تشغيل دخول التطبيق أو الترخيص، وأصبحت مقارنة PDF تسبق قياسات SQLite الطويلة. يظل فشل أي مقارنة مانعاً لبناء الحزم.

إعادة التشغيل: `scripts/benchmark-voucher-pipeline.ps1 -Label core` بعد وضع نسخة SHA الأساس في `.pipeline-baseline`. المخرجات في `out/voucher-*.jsonl`. نتائج GitHub Actions النهائية وروابط الحزم الأربع تُسجل في وصف PR بعد اكتمالها. لا دمج عند فشل، ولا بدء للمرحلة الخامسة.

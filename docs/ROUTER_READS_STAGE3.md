# المرحلة الثالثة: قراءة بيانات MikroTik

الأساس هو `bc26cedc2e60fbe2cbc778631c8b3cc6a2ad27f5` من `main` بعد دمج المرحلتين الأولى (#39) والثانية (#40). هذه المرحلة تخص القراءة والتخزين المؤقت فقط؛ لا تنفذ تحسينات توليد أو إرسال دفعات المرحلة الرابعة.

## الأخطاء المثبتة والتصحيح

- كانت تفاصيل كرت واحد تجلب كل تاريخ جلسات UM، ثم تجلبه دون projection مرة أخرى عند عدم وجود تطابق. أثبت اختبار قبل التعديل أن فتح حساب فارغ مرتين يسبب أربع قراءات جلسات كاملة. أصبح المسار يستعلم على الخادم عن اسم الحساب أو معرفه عبر aliases، مع OR واحد، ويقبل القائمة الفارغة الصحيحة دون إعادة تنزيلها.
- كان المحلل يقبل `start-time`, `end-time`, `session-time`, `session-status`, `address`، بينما الطلب لا يتضمنها. أصبحت قائمة الحقول توافق المحلل، وفي المستكشف القديم أيضا. غياب العداد/الحالة/التاريخ يبقى مجهولا، ولا يُستنتج النشاط من غياب وقت الانتهاء.
- كانت مهلة UM الضخمة تطبق حتى على سجل واحد و`count-only`؛ كما كانت العدادات تنتظر مسار تنزيل الحسابات. السجلات المحددة والعدادات تستخدم 20 ثانية للمحاولة ومسار الاتصال السريع. قراءة UM الكاملة أو تاريخ حساب ذي جلسات كثيرة يحتفظ بحد 10 دقائق ومهلة خمول دقيقتين. يسمح النقل بمحاولة قراءة إضافية واحدة عند الانقطاع؛ لا توجد إعادة كتابة تلقائية.
- كان UTF-8 التالف يترك بقية الرد في اتصال قابل لإعادة الاستخدام. أصبح خطأ بروتوكول يغلق الاتصال، ويعيد تهيئة القراءة المسموحة فقط. اختبارات TCP على loopback تثبت أن الكتابة لا تتكرر وأن الإلغاء أثناء رد جزئي يتخلص من الاتصال.
- كانت ذاكرة دورة الحياة تبقى بعد بعض تعديلات المستخدمين، وكانت قراءة جارية تستطيع إعادة نشر بيانات أبطلها تعديل. أصبح للذاكرة رقم مراجعة وحالة كتابة جارية؛ لا تنشر قراءة تداخلت مع التعديل. يشمل الإبطال الإنشاء والتفعيل والتعطيل والحذف وإسناد الباقات، والنتائج المؤكدة وغير المؤكدة. تعديلات الباقات تبطل تعريفاتها وقوائم المنشئ كذلك.
- كانت قراءات متزامنة من الصفحات تكرر نفس الجلب. تتشارك طلبات التحديث المتزامنة النتيجة المكتملة، وتنفذ عملية جرد ثقيلة واحدة في الوقت نفسه لكل gateway؛ تبقى العدادات والإحصائيات الخفيفة والتحقق بسجل واحد مستقلة. تُلغى قراءات إدارة الكروت عند تغيير التبويب/مغادرة الصفحة، وقراءة تفاصيل الكرت عند إغلاق النافذة.
- كان fallback لوحة Hotspot يحول عدادات ناقصة إلى صفر. يرفض الآن اعتماد جرد ناقص بعد محاولة التوافق. كذلك يتحقق جرد Hotspot وPPP من الحقول الضرورية قبل اشتقاق الحالة.
- كانت الواجهة تعرض وقت الرسم باعتباره وقت القراءة. تحمل النتائج وقت القراءة ومصدرها، وتعرض الحسابات والجلسات والباقات والتقارير والرئيسية ذلك؛ تفاصيل الكرت تحتفظ بالوقت عند الترقيم والتصفية، وقائمة المنشئ تراعي إبطال تعريفات الباقات.

## مراجعة القراءات

| المسار | القرار |
| --- | --- |
| تفاصيل جلسات حساب UM v6/v7 | استعلام equality مقيّد بالخادم؛ تحقق محلي من كل صف؛ لا fallback أوسع عند خطأ صلاحيات أو انقطاع |
| خادم لا يدعم مرشح الجلسات أو يتجاهله | تعلم عدم الدعم بعد دليل واضح، ثم لقطة كاملة مشتركة لمدة 20 ثانية؛ لا يُستنتج عدم الدعم من نتيجة فارغة |
| projection جلسات غير متوافق | محاولة واحدة بنفس المرشح دون projection، ثم حفظ حالة التوافق؛ لا إعادة طلب لمجرد غياب تاريخ أو عداد |
| جرد UM للحسابات ودورة الحياة | لقطة بلا كلمات مرور مشتركة لمدة 5 دقائق، مع force للتحديث الصريح وإبطال بعد الكتابة؛ fallback واحد للحقول الضرورية ثم تعلم التوافق |
| تعريفات الباقات والقيود وروابطها | طلب الحقول اللازمة فقط؛ ذاكرة الباقات 45 ثانية، وقائمة المنشئ دقيقتان؛ إصلاح سباق الإبطال في كليهما |
| Hotspot users، PPP secrets/profiles/active، Hotspot profiles/servers | projections للحقول المستعملة؛ لا تنزيل كلمات مرور PPP، بينما تبقى كلمة مرور Hotspot مطلوبة لوظيفة العرض الصريحة الحالية |
| Hotspot Active مع مصدر RADIUS | الإبقاء على القراءة الكاملة المقصودة: بعض v6 يحذف flags من projection؛ لا توجد كلمات مرور في هذا الجدول |
| إحصائيات الرئيسية | count-only فقط، دون fallback إلى جرد كامل؛ القيم غير المتاحة تبقى مجهولة |
| قراءة ما قبل الحذف/تأكيد الإرسال | تبقى مستقلة وحديثة، ولا تعتمد على ذاكرة العرض؛ أضيف دعم session ID إلى allowlist النقل الموجود |
| فحص تعارض أسماء دفعات الإصدار | لم يتغير في هذه المرحلة؛ الجرد الكامل عبر الخدمات مطلوب لهذا المسار الحالي، وتحسينه يتبع المرحلة الرابعة |

لا يزيد عدد اتصالات النقل عن المسارين الموجودين سابقا. تقليل حجم الردود لا يثبت وحده انخفاض CPU الراوتر؛ قد يفحص RouterOS جدوله داخليا لتنفيذ المرشح. لم يجر قياس على راوتر فعلي أو اختبار ضغط عليه.

## الاختبارات والقياس

فشلت **7 اختبارات سلوكية قبل تعديل كود الإنتاج**. أثبت اختبار إضافي قبل إصلاحه حجز جرد Hotspot لمسار الإحصائيات. أضيف إجمالا **28 اختبار Core** تشمل الحقول البديلة، النتيجة الفارغة، الخادم الرافض/المتجاهل للمرشح، عدم توسيع القراءة عند منع الصلاحيات، تعلم projection، التحديث المتزامن، توقيت اللقطة، الإبطال أثناء القراءة والكتابة، النتيجة غير المؤكدة، إلغاء الصفحة، وفشل UTF-8 ومهلات الطلبات وتسلسل البروتوكول عبر TCP محلي.

محليا: 472 Core و41 Delivery و261 فحص Python ناجحة، وترجمة الحل مع WPF ناجحة باستخدام مراجع Windows. اختبار DPAPI وواجهة WPF الفعلية واختبارات Desktop تنفذ في Windows CI. قوالب x86/x64 من Release تعمل بالتوازي مع Core؛ لا يبدأ التغليف إلا بعد نجاحها جميعا، بما فيها مقارنة القياس.

المحاكاة في `tools/RouterReadBenchmarks` لا تفتح socket ولا تقبل عنوان راوتر. نفس البيانات والعمليات تُشغّل على الالتزام السابق والكود الجديد لأحجام 1 و100 و1000 و10000 سجل. لكل حالة تسخين واحد وخمس عينات، ويُعرض وسيط الزمن المحلي. تحتوي التجهيزة على حقول إضافية غير مستخدمة (منها حقل 1024 بايت) لإظهار تكلفة القراءات غير المحددة؛ أرقام الحجم تخص هذه التجهيزة وليست توقعا لكل راوتر.

- `response_bytes`: حجم الردود الاصطناعية بعد UTF-8 مع بادئات أطوال الكلمات و`!re/!done`؛ لا يتضمن TCP/TLS أو تسجيل الدخول أو حجم الطلب.
- `local_median_ms`: زمن محلي للمحاكاة والتحويل فقط، يتأثر بالجهاز وGC؛ ليس زمن استجابة راوتر حقيقي.
- `modeled_network_ms`: نموذج معلن = عدد الطلبات × 5ms + بايتات الرد ÷ 1MiB/s؛ ليس قياس شبكة فعليًا.
- حالات التفاصيل هي أربع زيارات: موجود، فارغ، موجود، فارغ. جرد UM المشترك يحاكي عرض الحسابات ثم الرئيسية. العدادات الأخرى تخص جردًا واحدًا.
- الملفات الخام: [قبل](benchmarks/router-reads-stage3-before.jsonl) و[بعد](benchmarks/router-reads-stage3-after.jsonl). ترفض المقارنة أي فقد سجلات أو خطأ أو إعادة محاولة أو زيادة في الطلبات/حجم الردود؛ لا تستخدم عتبة زمنية متذبذبة لإخفاء فشل صحة البيانات.

تُعاد المقارنة على Windows في Core وRelease وتُرفع النتائج كـ artifacts. لإعادة القياس محليا: استنسخ الأساس `bc26ced` في `.benchmark-baseline` ثم شغّل `./scripts/benchmark-router-reads.ps1`. ينسخ السكربت تجهيزة الاختبار نفسها ويشغلها بـ `Stage3=false` على الأساس و`Stage3=true` على التعديل، ثم يستدعي `compare.py`.

## الحدود

لم تتغير صيغة قاعدة البيانات أو التراخيص أو الطباعة أو آلية تأكيد إنشاء الكروت. لا حذف أو إرسال فعلي إلى راوتر أثناء هذه الاختبارات. الاختبار الميداني على إصدارات RouterOS المختلفة باقٍ، وتبقى البيانات الناقصة مجهولة. الذاكرة مؤقتة ومحصورة في gateway الاتصال الحالي، ولا يُستخدم تاريخ جلسة أو لقطة محفوظة كإذن للحذف. لم تبدأ المرحلة الرابعة.

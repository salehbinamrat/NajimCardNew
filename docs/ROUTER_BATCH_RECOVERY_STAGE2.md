# المرحلة الثانية: ربط الدفعات بالراوتر واستعادة الإرسال المتوقف

## الأساس والنطاق

دُمج PR #39 بعد اعتماد المتابعة والتحقق من نجاح Windows Core وRelease والحزم الأربع.
أُنشئ فرع هذه المرحلة من أحدث `main`: `2c20b77b6922ee4b9d80bb49f32f9e349d6d11de`.
لا يشمل العمل المرحلة الثالثة أو إعادة تصميم الصفحات أو تغيير الترخيص.

## الأخطاء المثبتة

- المفتاح القديم `(service, username)` لا يميز راوترين يستخدمان الاسم نفسه.
- لا تتضمن الدفعات ولا قوالب طباعتها هوية الراوتر؛ الاتصال الحالي كان يستطيع إرسال سجل مجهول الملكية.
- كانت الحالات `SENDING` و`UNKNOWN` محمية من إعادة الإرسال المباشر، لكن بلا مسار مطابقة واستئناف.
- إعادة الاتصال لم تكن تتحقق من أن الجهاز البديل هو الجهاز نفسه.
- نتيجة الإرسال لم تكن مرتبطة بمعرّف محاولة مستقل، ولم يكن هناك تاريخ متتابع لكل كرت.

بدأ العمل بخمس حالات اختبار فشلت جميعها على الكود السابق قبل تعديل الإنتاج.
اختُبر كذلك رفض تصدير دفعة تجمع راوترين قبل إصلاحه، وتوافق المطابقة مع غياب حزمة User Manager.

## الحماية الجديدة

هوية الجهاز مشتقة من رقم RouterBOARD التسلسلي، أو `system-id` لـCHR، أو `software-id`
للأنظمة التي لا تقدم المصدرين الأولين. تُحفظ بصمة المصدر والقيمة؛ لا يُستخدم IP أو اسم
الجهاز أو المستخدم لإثبات الملكية. عدم توفر الهوية يمنع الإصدار والمطابقة. بعد تثبيتها،
تتحقق جلسة الاتصال من كل اتصال بديل في مساري القراءة والإرسال قبل استعماله.

أصبح المفتاح `(router_id, service, username)`، وربطت سجلات الدفعات وقوالب الطباعة
والاستعلامات والسجلات الزمنية بهوية الراوتر. الاستعلام القديم دون تحديد الراوتر يرفض
الدفعات الملتبسة؛ لا يجمعها. يرفض التصدير والطباعة خلط راوترين.

تسبق أي كتابة شبكة معاملة `WAL + synchronous=FULL` تحفظ `SENDING` ومعرف محاولة فريدًا.
لا يقبل الإيصال إلا هذه المحاولة والكرت والراوتر. يسجل تغيير الحالة ووقت UTC والنتيجة
والمعرف البعيد عند توفره داخل المعاملة نفسها. فشل الحفظ بعد الشبكة يترك `SENDING`
محمية. يمنع قفل ملف حصري لدفعة واحدة التنافس بين الإرسال والمطابقة عبر عمليات التطبيق،
ويحرره نظام التشغيل عند توقف العملية.

## الترقية والبيانات القديمة

- قبل ترقية قاعدة قديمة تنشأ نسخة SQLite متسقة في `Backups/before-router-v2-*.db`.
- تنقل الجداول المطلوبة داخل معاملة واحدة؛ فشل النسخ يعيد المخطط والسجلات الأصليين.
- تبقى بايتات كلمات المرور المحمية بـDPAPI وقوالب الطباعة القديمة كما هي، دون فك تشفير.
- لا تُحذف جداول الإعدادات أو ملفات الترخيص، ولا تُعاد كتابة سجلات الترخيص.
- تبقى `router_id=''` للسجلات القديمة. يعرض سجل الدفعات ملكيتها كمجهولة ويمنع إرسالها
  أو نسبتها تلقائيًا إلى أي اتصال؛ تبقى السجلات ونتائجها السابقة قابلة للمراجعة.
- لا يجوز تشغيل نسخة قديمة من البرنامج على قاعدة البيانات المرقاة؛ للمراجعة قبل الترقية
  توجد النسخة الاحتياطية. لا تستبدل قاعدة حية بنسخة قديمة لإعادة إرسال دفعات سبق إرسالها.

## طريقة المراجعة والاستئناف

من نافذة **سجل الدفعات** الموجودة اختر الدفعة ثم **مطابقة مع الراوتر**. هذه العملية
للقراءة فقط على الراوتر؛ تتحقق من هويته ثم تستعلم بالاسم في الخدمات الأخرى أيضًا.

| النتيجة | الإجراء |
| --- | --- |
| `SENT` | الحساب وعلامة هذه الدفعة والمالك والباقة والتفعيل متطابقة؛ لا يُعاد إرساله |
| `READY` | ثبت غياب الاسم؛ يسمح زر الاستكمال بإرساله بعد تحقق مستقل جديد |
| `UNKNOWN` | قراءة ناقصة أو حساب موجود لم يتأكد تفعيل باقته؛ لا إنشاء أو تفعيل تلقائي |
| `CONFLICT` | الاسم موجود لحساب أو خدمة أو باقة أخرى؛ يلزم فحص يدوي |
| `SENDING` | محاولة لم يثبت إيصالها، بما فيها توقف البرنامج؛ يلزم المطابقة أولًا |

يعرض تبويب **تاريخ المحاولات والمطابقة** الانتقالات وأوقاتها ومعرف كل محاولة. لا يكتب
السجل الجديد كلمات المرور. يكمل زر **استكمال الكروت المثبت غيابها** حالات `READY` فقط،
مع إعادة فحص الهوية والأسماء والحالة المحفوظة. لا توجد إعادة إرسال آلية عند بدء البرنامج.

تضيف الإصدارات الجديدة علامة `NC2:` مشتقة من هوية الراوتر والخدمة والدفعة والاسم داخل
حقل `comment` للحساب الجديد. الاسم وحده لا يكفي لاعتماد حساب موجود. لا تُعدل علامات
أو حسابات المستخدمين الموجودة مسبقًا أثناء المطابقة.

## التحقق والحدود

المشروع الجديد `NajmCard.Delivery.Tests` يختبر الشفرة الإنتاجية للتخزين والإرسال باستخدام
SQLite فعلية ومحاكاة راوتر في الذاكرة. تستخدم الحالات المشتركة بين الأنظمة كروت بلا كلمة
مرور؛ اختبارات Windows الموجودة تستمر في اختبار DPAPI الفعلية. تغطي الاختبارات تغيير
الجهاز، تكرار الأسماء، القنوات المعاد توصيلها، الترقية وتراجعها، فقد رد الإنشاء أو التفعيل،
إعادة فتح البرنامج، الإيصالات القديمة، المطابقة المتزامنة والاستئناف والطباعة المعزولة.

لم يُرسل أي كرت إلى راوتر حقيقي في الاختبارات. النجاح الآلي لا يحل محل التحقق الميداني
من ردود إصدار RouterOS المستخدم. إذا تغير معرف الجهاز بسبب إعادة تثبيت النظام أو استنساخه
فلن تنسب الدفعات إليه تلقائيًا. لا يوفر RouterOS معاملة ذرية تضم الاستعلام والإنشاء؛ تبقى
التعديلات الخارجية المتزامنة خارج ضمان التطبيق، وتبقى أي نتيجة ناقصة محجوزة للمراجعة.

Windows Core وRelease يعملان بالتوازي على الالتزام نفسه، ويختبران الاستعادة قبل السماح
ببناء x86/x64 Portable وInstaller. تسجل النتائج النهائية وروابط الحزم في طلب الدمج.
